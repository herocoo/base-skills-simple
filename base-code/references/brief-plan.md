# 任务单:实现计划 {{group}}

> 主会话把 `{{变量}}` 替换成实际值后写入 `{flowDir}/briefs/plan-{group}.md`,再委派给 base-planner,或内联执行。

为 `{{group}}` 生成实现计划。**本轮只产出计划,不写任何业务代码,不提交。**

## 基准

- 读源码、执行命令:一律在 `{{workDir}}` 内(当前应已在功能分支 `{{branch}}` 上)。
- 计划写到 `{{planPath}}`(绝对路径,在 `.base/dev/` 下,不在源码仓库里)。
- 不写 `flow-state.json`,不提交,不改动 `{{workDir}}` 内的任何文件。

## 输入

- 技术方案(必读):`{{design}}`
- API 契约(本 group 产出的 + 所依赖 group 的,有则读):
{{apiContracts}}
- 代码探索报告:`{{explore}}`(无则写"无")
- 既有计划(重做时才有,在其基础上改):`{{existingPlan}}`
- 修订说明(重做时才有):
{{revisionNote}}

## 任务(工具调用预算 ≤ 15 次)

1. 读技术方案与契约,确认要实现的范围(接口签名、字段、流程)。
2. 定向探查:用搜索定位相邻模块与既有模式,只读关键行段;**不整文件读大文件**。
3. **测试框架与基线(1–3 次)**:先确认本 group 的测试框架和运行命令(取自探索报告或构建文件)。**没有测试框架**:不要自行决定,也不要在计划里假装有测试,返回 `blocked`,reason 写"仓库无测试框架,建议搭建 {该技术栈的主流框架},或确认本次不写自动化测试"(用户选后经修订说明回到你这里)。然后,计划里凡要写"零错误 / 全部通过"这类验收条件(类型检查、lint、编译、既有测试),先在当前 HEAD 上跑一次对应命令(输出只取末尾 20 行)。基线本身不满足,就把条件改写成"**不新增**错误(基线 N 个)",并写进"风险与待确认"。
4. 写计划到 `{{planPath}}`。

```markdown
|---|---|---|

模块: {模块名}

- 跑 `{具体命令}`,确认失败(原因应为功能缺失)

- 跑 `{具体命令}`,确认通过
- 提交 `feat({{group}}): {模块描述}`

### [ ] 任务 2: ...

## 风险与待确认
- {需要用户裁决的点;无则写"无"}
```

## 硬要求

- **无占位符**:每步都是能直接执行的完整内容。禁止 `TBD`、`补上错误处理`、`同任务 N`。
- **签名一致**:接口签名在各任务里逐字一致,并与 API 契约对齐。
- **按模块分任务**(提交边界),不按技术层分;遵循探索报告里的"既有约定"。
- **测试先行**:每个任务的测试步骤在实现步骤之前,"跑测试"写出能直接执行的具体命令(单文件或单用例)。纯配置、文档、脚手架类变更并入所属任务,不单独拆。修订说明里若写明"用户确认本次不写自动化测试",任务里省略测试步骤,并在计划开头写一行 `测试: 无(用户已确认)`。
- **任务粒度**:一个任务一次提交,能独立跑测试通过。
- **体积**:计划 ≤ 64 KB(软限)。不抄技术方案原文,只写"做什么、在哪做、怎么验"。超标先删已决策的风险项与重复说明,**不删任务步骤或测试用例**;删完仍超则在首行写 `> 体积 X KB / 目标 64 KB` 后交付。
