# base-prod 产品文档

把用户的需求整理成 `prod-design.md`。主会话内完成,不使用子代理。

## 0. 先读协议

读 `references/protocol.md`(读不到试 `.kiro/skills/base-prod/references/` 与 `~/.kiro/skills/base-prod/references/`)。按 §1 完成入口。本阶段无前置阶段。

## 1. 执行

1. **头脑风暴(澄清需求)**:最多 2 轮,按协议 §3 提问。
   - **先看再问**:用户提到的文件、设计稿、现有页面先读;上下文里已有答案的不问。
   - **第 1 轮**(用户还没给需求就先请其描述;需求已清楚就跳到第 2 轮):用自己的话复述需求(≤200 字,只写用户说过的,你补的标"我的假设"),指出你发现的冲突或更省的做法。用户没说"为什么做、做成什么样算成功"时,补问一个**开放问题,不给选项**(用户自己的话比你的选项准)。
   - **第 2 轮**:一次问全影响范围与边界的决策。每题说明答案会改变什么,先亮推荐与理由;问题要具体到本需求、顺着用户上一个回答问,不问通用清单。并入原型评估(第 3 步)与涉及项目清单(名称、类型、路径、是否对外暴露 API;用户已有答案就问出,避免 base-tech 再问)。
   - **要覆盖**(不要当清单念):目标用户与场景、成功标准、**非目标**(明确不做什么)、用户见过或用过的参考做法、现状、用户在意的细节。
   - 实为多个独立项目 → 说明并商定拆分与顺序,本流程先做第一个。用户说"你定" → 给出具体方案,记为"我的假设"。
2. **生成文档**:读 `assets/prod-design-template.md`,按结构写入 `{flowDir}/prod-design.md`。用户没说过、由你补的内容一律写进"我的假设",不当作用户已同意。验收标准每条写成"当 {条件} 时,系统应 {行为}",覆盖核心正向流程、主要异常、权限边界。
3. **原型评估**(仅"涉及项目"含 frontend 时):HTML 原型很贵(一页 10–30k 输出 token,且会被后续阶段反复读),**默认不出**。出现新页面、新交互模式、多角色或多状态页面、用户明确要求时才建议出;已有设计稿、仅改字段或文案、布局文字能唯一确定时不出。把推荐与理由并入第 2 轮的提问,选项为 `不出` / `低保真线框` / `高保真`。出原型时写单文件 `{flowDir}/demo.html`(用绝对路径;原型不是项目代码,**只写进 `{flowDir}`,不写进工作区根目录或"涉及项目"的目录**,即使需求的交付物本身也叫 demo.html;写完用 `ls` / `Test-Path` 确认文件在 `{flowDir}` 下):纯静态、无构建、无外部依赖,只覆盖"页面布局"列出的页面,低保真 ≤15 KB、高保真 ≤40 KB。在 prod-design"页面布局"末尾记一行 `原型:demo.html(低保真/高保真)` 或 `原型:不出(理由)`。
4. **重做**(entry=redo):先读已有 `prod-design.md` 与 `stages.prod.note`,在其基础上改;已有 `demo.html` 且反馈不涉及页面就不重生成,涉及则只改受影响的页面。

## 2. 闸门与衔接

1. 按协议 §3 走阶段闸门(通过 / 不通过 / 跳过);摘要里单列"非目标"与"我的假设"供核对。不通过:按反馈修改后重审。跳过:`status=skipped`,`note` 写原因。
2. **通过**:写 `stages.prod.status=approved`;`entry=redo` 时按协议 §6 级联失效下游。
3. 按协议 §7 输出交接提示,下一步 `/base-tech`。
